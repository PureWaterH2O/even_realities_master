## Terminal Mode & Usage <a id="terminal-mode"></a>

**Summary.** Even G2 "Terminal Mode" is an official, built-in feature (not a third-party SDK app, and unrelated to the Even Hub "terminal" naming which just refers to a Claude Code CLI) shipped in the Even Realities iOS/Android app v2.2.0 (live ~Apr 27-30 2026), with Codex support added in v2.2.1. It turns the G2 glasses into an ambient control surface for AI coding agents: the agent's running output "tail" appears in the green HUD, status is glanceable (Thinking/Listening/Executing), and you respond hands-free via the R1 ring (single tap = confirm/approve, double tap = reject) or by holding the ring or glasses touchpad to dictate a voice instruction via the 4-mic array. You enable it in the Even app Settings and pair a host machine by its info, port, and auth token, in practice by scanning a QR code printed by the official @evenrealities/even-terminal npm CLI (current 0.7.9). That CLI runs a local Express + SSE bridge server (default port 3456, bearer-token auth) that drives Claude via @anthropic-ai/claude-agent-sdk and Codex via `codex app-server` JSON-RPC over WebSocket (port 8765). The bridge condenses each tool call to a single line for the tiny 576x288 display, surfaces permission/question prompts as ring-answerable options, and supports multi-session monitoring (running/blocked/waiting). I independently re-verified the package internals against the cryptographically-confirmed official npm tarball (shasum bbf831b7c2dfcb5be480f516f5af716510fb4cac): the Claude path hard-codes model claude-opus-4-6, permissionMode acceptEdits, and maxTurns 50 in dist/claude/session.js (lines 241/248/268), and permission prompts genuinely default to DENY after 60s while AskUserQuestion defaults to SKIP after 120s (session.js lines 471 and 418). One earlier adversarial verdict that "refuted" the timeout behavior was itself mistaken: it audited third-party forks (a sandbox repo and the OpenClaw fork) rather than the official package, whose source confirms the original claim exactly. Key limits: text-heavy reading is awkward on the small display (community consensus: long output is better as audio), the hard-coded claude-opus-4-6 is now two model generations behind (Opus 4.7 and 4.8 have shipped), and enabling Terminal Mode reportedly suppresses normal G2 dashboard/general features (single community report). The G2 has no native terminal-text rendering primitive in the public SDK; the closest low-level analog is the reverse-engineered teleprompter BLE service.

- ✅ **The bearer token is accepted as a plaintext ?token= query parameter in addition to the Authorization: Bearer header.** — dist/index.js auth middleware (lines 25-35): `const queryToken = req.query.token; const provided = header?.startsWith("Bearer ") ? header.slice(7) : queryToken; if (provided !== TOKEN) { ...401... }`. So `GET /api/...?token=<TOKEN>` authenticates exactly like the header. This is structurally necessary because the only realtime channel is Server-Sent Events at GET /api/events (dist/routes/events.js), and browser/EventSource clients cannot set Authorization headers — so the token MUST travel in the URL for the event stream. The default token is a random 16-byte hex string (`randomBytes(16).toString("hex")`, index.js line 11) unless overridden by the BRIDGE_TOKEN env var or the --token CLI flag. [gap-fill] [s109]
- ✅ **The token is leaked into multiple plaintext sinks: server request logs, stdout/QR connect URL, and (when exposing) the public tunnel URL.** — Three concrete leakage paths in the source: (1) Request logging — dist/index.js lines 15-22 log `${req.originalUrl}` which includes the full `?token=...` query string, so the token is written to console/log file on every request. (2) Console banner — dist/startup/common.js line 277 prints `Full token: ${token}` in cleartext and line 284 builds a connect URL `http://${address}:${port}?${params.toString()}` (params include `token`) which is also rendered as a QR code. (3) Public expose — dist/expose/run.js line 51 constructs `const fullUrl = \`${parsedUrl}?token=${token}\`` and prints it plus a QR code, embedding the secret directly in a publicly-reachable tunnel URL. Anyone who sees the QR, the terminal scrollback, or the logs obtains full bridge access. [gap-fill] [s109]
- ✅ **The bridge itself runs plain HTTP with no TLS, and CORS is fully open.** — dist/index.js creates a plain Express app with `app.use(cors())` (line 14, no origin allowlist) and starts it with `app.listen(...)` over HTTP — there is no https.createServer, certificate handling, or TLS anywhere in dist/. ## App / SDK Development <a id="sdk-app-dev"></a>

**Summary.** Even Realities G2 apps ("plugins") are web apps (HTML/CSS/TS) that run inside the Even Realities phone app's WebView (Chromium on Android, WKWebView on iOS); the phone acts as a BLE proxy and the glasses only render UI containers and emit input events — no app code runs on the glasses. The single first-party developer dependency is the official npm SDK @evenrealities/even_hub_sdk (latest v0.0.10, released 2026-04-10), accompanied by @evenrealities/evenhub-simulator (v0.7.2) and the @evenrealities/evenhub-cli (v0.1.12, binaries evenhub/eh). The SDK injects a typed EvenAppBridge into the WebView (obtained via waitForEvenAppBridge) with a container-based render model: createStartUpPageContainer (once), rebuildPageContainer (full redraw, brief flicker), textContainerUpgrade (faster, flicker-free in-place), updateImageRawData (sequential only — no concurrent sends), shutDownPageContainer (immediate or confirmation dialog). A page allows up to 12 containers total (max 4 image + max 8 text/list); display is 576x288 px per eye, 4-bit greyscale (16 shades of green), with a single LVGL firmware font and no font-size/selection control. Device APIs cover audioControl (16kHz s16le mono PCM, delivered via event.audioEvent.audioPcm), imuControl (ImuReportPace P100-P1000 ms between reports, not Hz), getDeviceInfo (DeviceModel g1/g2/ring1, battery/wearing/charging/inCase), getUserInfo, and a string KV store (setLocalStorage/getLocalStorage that persists across reboot, unlike unreliable browser localStorage/IndexedDB in the WebView). Input events route by container type (textEvent for scroll, listEvent for selection, sysEvent for clicks/system/IMU). Critically, the R1 ring and the two temple touchpads SHARE the same event types (OsEventTypeList CLICK=0..IMU_DATA_REPORT=8) and are distinguished ONLY via EventSourceType (ring = TOUCH_EVENT_FROM_RING = 2) — there are NO dedicated RING_* event types in the official SDK (the brianmatzelle template's RING_CLOCKWISE/COUNTER_CLOCKWISE/CLICK constants are a disproven community invention). Networking is gated twice: an app.json HTTPS-only origin whitelist (no wildcards) plus normal browser CORS. Apps package into .ehpk via the CLI, undergo manual review, and distribute over-the-air through the Even Hub store launched 3 Apr 2026 (~50 launch apps, 2000+ devs). Any web tech works (official templates are Vite+TS; community uses React, Kotlin Multiplatform, etc.) on a Node 20/22 toolchain, with no native-on-glasses code. Distinguish this Even Hub web-SDK stack (G2) from the older G1-era raw dual-BLE protocol (EvenDemoApp).

## BLE / Firmware / Protocol <a id="firmware-ble"></a>

**Summary.** The G2 and G1 use fundamentally different BLE architectures. G1 (older) exposes two independent Nordic UART Service (NUS) radios — one per arm — with a flat 1-byte-opcode protocol (0x0E mic, 0x15 BMP, 0x4E text, 0xF1 LC3 audio, 0x25 heartbeat, 0xF5 touch/AI, responses 0xC9/0xCA/0xCB), and the phone must send left-then-right with ACK. G2 instead exposes a custom GATT service under base UUID 00002760-08c2-11e1-9073-0e8ac72eXXXX with three channel pairs — Control (write 0x5401 / notify 0x5402), Display (0x6401/0x6402) and File/OTA (0x7401/0x7402) — and a framed transport: an 8-byte header starting with magic 0xAA, a type byte (0x21 cmd / 0x12 resp), sequence, length, packet-total/serial (fragmentation), a 2-byte service ID, then a protobuf payload and a 2-byte little-endian CRC-16/CCITT (init 0xFFFF, poly 0x1021, computed over payload only). Sessions begin with a 3-packet (fast) or 7-packet (full) auth/capability+time-sync handshake on service 0x80-xx, kept alive by a Type-14 heartbeat. Features are addressed by 2-byte service IDs (teleprompter 0x06-20, conversate/STT 0x0B-20, navigation 0x08-20, even-AI/dashboard 0x07-20, device info 0x09-00, etc.). G2 also retains a legacy NUS-compatible opcode layer (0xF5/0x0E/...) used mainly for simple gestures and R1-ring relay. The G2 hardware BOM (Ambiq Apollo510-class Cortex-M55 SoC + separate EM Micro EM9305 BLE 5.4 radio over HCI running a Cordio host stack, Macronix 32MB QSPI NOR with LittleFS, JBD micro-LED 576x288 4-bit, single PDM MEMS mic via GX8002B codec, LC3 audio) comes from ONE firmware reverse-engineering project (openCFW) and is plausibility-corroborated by vendor marketing (Ambiq/EM Micro/Even's own blog) but NOT confirmed by any independent teardown or datasheet; the exact "Apollo510b" SKU is an inference (the only binary string is build_path_ap510, with no "b") and is internally inconsistent with a separate EM9305 because the 510B has an integrated BLE radio. The G2 advertises as "Even G2_32_L/R_xxxxxx" (two peripherals, one per eye, synced over a 0.1mm FPC rather than wirelessly) and is Bluetooth 5.4 with PAwR. Analyzed production firmware string v2.0.7.16 (build 2026-02-13). G2 firmware updates use a custom "EVENOTA" multi-image protocol over the 0x7401/0x7402 file channel, ECDSA P-256 signed — NOT Nordic DFU. The R1 ring is a physically separate Nordic nRF5x device (FCC ID 2BFKR-R01) with its own GATT service (BAE80001-4F05-4503-8E65-3AF1F7329D1F, TX BAE80012, RX BAE80013), SoftDevice BLE stack, MCUboot, and Nordic FE59 Buttonless Secure DFU + MCUmgr/SMP firmware updates; the previously claimed "nRF52840 SoftDevice-S140 DFU as a G2 auxiliary path" is DISPROVEN — that Nordic pipeline belongs entirely to the Ring, not to the glasses, and the G2 plays no role in Ring firmware updates. The R1 sends [0xFF][gesture][param] gesture frames that the phone decodes and relays to G2. NOTE: nearly all protocol-level detail (UUIDs, opcodes, service IDs, framing) comes from two community reverse-engineering projects (i-soxi/even-g2-protocol and kalanihelekunihi/evenRealities-openCFW); Even Realities publishes no low-level BLE spec, the two projects disagree on several service-ID assignments, and the G2/R1 FCC filings have confidential block diagrams that neither confirm nor refute the silicon.

### Limitations

- Nearly all protocol-level detail (base UUID 0x2760, channel suffixes, 8-byte 0xAA framing, CRC-16/CCITT over payload, 2-byte service IDs, protobuf schemas, auth/heartbeat sequences) derives from two community reverse-engineering projects (i-soxi/even-g2-protocol and kalanihelekunihi/evenRealities-openCFW). Even Realities publishes NO official low-level BLE specification, so none of it is vendor-confirmed.
- The two RE projects disagree on several G2 service-ID assignments (e.g. 0x07-20 Dashboard vs EvenAI, 0x01-20/0x02-20/0x05-20/0x91-20/0xE0-20/0x81-20 documented only by openCFW). Any single-project-only service ID is provisional.
- The entire G2 hardware BOM (Apollo510-class SoC, EM9305 radio, GX8002B, JBD4010, CY8C4046FNI, ICM-45608, nPM1300, MX25U25643G) rests on a single firmware-RE source (openCFW). It is plausibility-corroborated by vendor marketing but NOT confirmed by any independent FCC teardown or datasheet.
- The exact main-SoC SKU is unresolved: the only binary string is 'build_path_ap510' (no 'b'), openCFW cannot distinguish Apollo510 from Apollo510b, and the 'separate EM9305' evidence is internally inconsistent with the 510B (which has an integrated BLE radio), pointing instead to the plain Apollo510.
- The R1 Ring's exact Nordic SoC SKU and SoftDevice naming (nRF52840 / S140) are rated only MEDIUM confidence by openCFW itself ('no specification sheet confirms nRF52840 or S140 naming').
- The G2 (FCC ID 2BFKR-G2, granted 2025-11-23) and R1 (FCC ID 2BFKR-R01) FCC filings exist but have confidential block diagrams/schematics/operational descriptions, so they neither confirm nor refute the chipset claims.
- Firmware analyzed was production string v2.0.7.16 (build 2026-02-13) with bundled Nordic DFU artifacts at v2.0.3.0004; protocol/service details may differ in other firmware versions.
- Cryptographic auth was NOT observed at the link layer (no challenge/key exchange seen during the G2 handshake); the security model beyond ECDSA-P256-signed OTA is uncharacterized.
- i-soxi flags the G2 notification (0xC4/0xC5 file-transfer) flow as 'partial', so the notification protocol is not fully mapped.

## Hardware & Specs <a id="hardware"></a>

**Summary.** The Even Realities G2 (launched Nov 12 2025, $599) is monochrome-green micro-LED display glasses with no camera and no speaker. ### Limitations

- The entire detailed component BOM for both the G2 (SoC, BLE radio, flash, micro-LED panel, IMU, ALS, touch, codec, power chain, case MCU) and the R1 (MCU) derives from a SINGLE low-profile community reverse-engineering repo (kalanihelekunihi/evenRealities-openCFW, 1 star). Adversarial verification found no independent second source and no first-party confirmation; all part IDs are firmware-derived (driver filenames, build paths, memory maps), not from a physical teardown, die markings, or schematics.
- The openCFW BOM contains an internal architectural inconsistency: the named main SoC (Ambiq Apollo510B) has an INTEGRATED Bluetooth LE 5.4 radio per Ambiq's own datasheet, yet the BOM also lists a SEPARATE external EM9305 BLE radio. This suggests possible conflation (either the '510b' suffix or the EM9305 attribution may be wrong); a base Apollo510 (no radio) + EM9305 would be more coherent.
- The claimed '512 KB SRAM' for the Apollo510B is imprecise: Ambiq lists 3.75 MB total system SRAM for the part; 512 KB matches only the Data TCM subset.
- The authoritative first-party source for chip identities (FCC ID 2BFKR-G2, granted 2025-11-23) exists with internal photos published, but its block diagram, schematics, and operational description are under short-term confidentiality (metadata only), and the published internal-photo PDFs could not be visually inspected via available tooling, so they neither confirm nor refute the part numbers.
- Several exact figures are not published by any source: G2 and case battery mAh capacities; R1 ring weight, physical dimensions, and battery mAh.
- One minor spec conflict was noted upstream (IP67 vs IP65 on different official G2 pages) but was not resolved in verification; it is not reflected as a separate finding here pending confirmation.
- Even Realities' own engineering and design blogs deliberately withhold all vendor/part identities, confirming only generic descriptors ('new processor', 'Bluetooth 5.4', 'micro-LED'), so no chip-level claim can currently be first-party verified.

## Ecosystem <a id="ecosystem"></a>

**Summary.** The Even Realities G2/R1 ecosystem is young (most activity dates from Feb-May 2026) but growing fast, anchored by two pillars: (1) the official Even Hub app platform launched April 3, 2026 (distributed OTA through the companion app's plugin gallery), and (2) a vigorous community/reverse-engineering scene on GitHub and Discord. NOTE ON LAUNCH METRICS: the widely-repeated "~50 launch apps" and "2,000+ developers" figures trace to a single Even Realities press release and are NOT independently verified; an independent outlet (Next Reality) reports there was "no stated launch app count, no named developer partners, and no revenue share or approval criteria publicly available" at launch, so these figures are downgraded to a single-sourced company claim. The official companion software split into two apps: a new "Even Realities" app (v2.2.2, May 2026) for G2 + R1 ring, and a separate legacy "Even G1 App." Terminal Mode (app v2.2.0, late Apr 2026) for controlling AI coding agents is the flagship recent feature. Two official Discords exist (developer support + broader user community), plus an independent reverse-engineering Discord. The most influential community maintainers are nickustinov (even-g2-notes reference + ~8 reference apps), fabioglimb (even-toolkit React/SDK library), and i-soxi (even-g2-protocol BLE reverse-engineering, the most-starred community repo at 142 stars); only nickustinov and fabioglimb are officially endorsed. Over 100 G2 community repos now exist spanning games, utilities, AI-agent bridges, and unofficial BLE transport kits. Maturity is still early: third-party app quality is uneven, the G2 installed base is undisclosed, no public revenue-share model exists, and open-source companion apps (Gadgetbridge) still support only G1, not G2. CAUTION: community technical write-ups can be unreliable on hardware specs — e.g. the OpenClaw bridge blog cites a 576x136 monochrome display, which matches neither the documented G2 (640x350 monochrome green micro-LED) nor the G1 (640x200) nor the reverse-engineered SDK canvas (576x288); treat hobbyist spec figures with skepticism. G2 is clearly distinguished from the older G1 throughout: G1 used a separate legacy app and is the target of older EvenDemoApp/Gadgetbridge/AGiXT tooling, while the Even Hub web-app platform and R1 ring are G2-only.
